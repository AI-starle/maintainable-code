# TSRPC 项目规范

## 适用与优先级

用户指定 TSRPC，或通过 `package.json`、锁文件、`tsrpc.config.ts` 和服务入口确认使用 TSRPC 时应用本规范。仅使用客户端 SDK 的项目只应用相关的协议共享与客户端约定，不凭空增加后端目录。

**必须遵循与项目版本、模板相匹配的 TSRPC 官方目录结构和命名规则。** 通用架构示例仅用于组织框架约定之外的业务实现，不能将协议和 API 文件搬入自创的 `features`、`controllers`、`adapters` 等结构。

先检查实际版本、所用脚手架模板、`tsrpc.config.ts`、启动入口及 `package.json` 脚本，确认协议输入、生成输出、API 加载和共享同步四条路径。设计目录、修改配置或新增接口时核对对应官方文档或官方模板源码；不要求每个局部业务修复都重新获取整套文档。

区分官方默认路径和配置允许的自定义路径：已有合法配置应保持一致，不为恢复默认值迁移全仓；新项目优先采用官方模板默认结构。官方模板随版本变化，不把此处示意当作永久标准。若配置与服务加载不一致，先识别实际断点，不依据示例改名掩盖问题。

注意：`tsrpc/tsrpc` 是框架源码仓库，其自身目录不等于使用 TSRPC 开发应用的标准目录。应用结构以官方应用脚手架和使用文档为依据。

## 官方约定的核心结构

以下为全栈项目的核心路径示意，省略启动文件等随模板变化的内容。纯后端项目不强制增加 `frontend` 或额外套一层 `backend`，以所用官方模板为准。

```text
backend/
  tsrpc.config.ts
  src/
    api/
      user/
        ApiLogin.ts
    shared/
      protocols/
        user/
          PtlLogin.ts
        serviceProto.ts
frontend/
  src/
    shared/                # 通过项目配置从后端共享；可能为链接或同步副本
```

- 协议默认位于后端 `src/shared/protocols`，API 实现默认位于后端 `src/api`；配置自定义路径时，以有效配置和服务端实际加载目录为准。
- API 协议文件为 `Ptl{接口名}.ts`，在文件内导出 `Req{接口名}` 和 `Res{接口名}`，可引用共享目录内的类型。消息协议文件为 `Msg{消息名}.ts`，导出 `Msg{消息名}`。
- API 实现文件为 `Api{接口名}.ts`，导出同名异步函数，通过 `ApiCall<Req类型, Res类型>` 处理请求与响应。
- API 实现与协议保持相同的相对子目录，例如 `protocols/user/PtlLogin.ts` 对应 `api/user/ApiLogin.ts`，服务名为 `user/Login`。不为了命名统一删除官方前缀或改成个人偏好的文件命名风格。
- `serviceProto.ts` 是生成产物，不手工维护其协议结构或服务标识，不为处理冲突或格式问题删除后重新编号；通过项目配置的生成流程更新并检查差异。`Api*.ts` 即使由工具初始化，也是后续需要维护的实现文件，不得当成可覆盖的生成产物。
- 协议及共享类型不得依赖服务端专属实现、数据库连接、密钥或 Node 专属能力。外部依赖应确认在共享端均可用，并与协议生成工具兼容。
- 确认共享源目录与同步目标，修改源端并保留现有链接或同步机制；不手工维护两份协议，也不把符号链接替换为普通副本。

## 在官方结构内实现可维护性

API 文件负责框架交互、权限与业务校验的衔接、调用业务能力及响应映射；复杂规则按仓库惯例提取到后端内部业务模块。`services`、`domain`、`repositories` 等仅为可选扩展，不能宣称是官方强制目录，也不为简单 API 创建空层次。

让核心业务尽量不依赖 `ApiCall`，将实际需要的数据传入业务函数。TSRPC 的类型校验不能替代授权、业务不变量和数据库约束；已经由框架保证的类型无需每层重复验证。按官方 `call.succ`、`call.error` 方式结束响应，避免同一路径重复响应。

新接口使用框架既有错误通道，成功响应直接表达业务结果，避免另造重复的 `code/message/data` 错误包装。既有公开协议的调整先评估兼容性，不因整理格式删除字段。客户端检查 `callApi` 返回的 `isSucc` 分支，失败时处理 `err`；不只依赖 `try/catch` 判断调用成功。

## 修改与验证

新增或修改接口时同步检查协议、实现、生成产物和客户端调用；仅修改实现且协议未变时不强制重新生成。先检查脚本定义，再按需运行仓库已有的协议生成、共享同步、类型检查和相关测试；`proto`、`sync` 等只是常见脚本名，不假定项目一定存在。不要为验证而无条件安装最新脚手架或启动长期服务。

移动或重命名协议会影响服务路径和客户端调用，不把它视为纯目录整理。必须检查兼容性及配置、加载、生成和共享路径；改变必填字段、类型或响应形状时，评估新旧客户端与服务端组合。交付时说明关键路径差异及实际验证；无法核对官方资料时如实说明，不将推测描述为官方标准。
