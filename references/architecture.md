# 目录结构与模块边界

## 选择结构

先遵守框架和仓库既有约定，再根据业务规模安排目录。示例不是统一模板，只创建有实际内容和职责的目录，不为了展示完整架构创建空目录或占位层。

TSRPC 项目必须先应用 [TSRPC 项目规范](tsrpc.md)，不直接使用下方的通用业务模块目录树替换官方协议和 API 目录。

判断边界时检查三件事：一条业务规则由谁维护；常见需求会改动哪些模块；跨模块调用是否只依赖必要契约。沿依赖箭头检查能否形成回路。目录名本身不能证明高内聚或低耦合。

| 场景 | 优先选择 | 拆分信号 |
| --- | --- | --- |
| 脚本、小工具、单一流程 | 少量文件，入口与核心函数清晰分离 | 多个独立变化点或外部依赖使阅读、测试困难 |
| 多个业务功能的应用 | 按业务能力组织模块，内部按需分层 | 一次功能修改经常横跨全仓技术目录 |
| 规则复杂、接入多个外部系统 | 模块内区分核心规则、用例和适配器 | 核心规则被数据库或传输协议牵制 |
| UI 应用 | 沿用路由和框架结构，按功能组织视图、状态及服务 | 组件同时承担渲染、业务决策与多种 I/O |
| 多应用或多包仓库 | 依据独立消费、发布或构建边界拆包 | 出现真实的独立生命周期，而非单纯文件增多 |

## 中等复杂度业务模块示例

下面展示订单功能需要规则与持久化边界时的一种结构。简单增删改查可以合并层次，文件扩展名依项目语言决定。

```text
src/
  orders/
    index                  # 面向其他模块的公开入口
    domain/
      order                # 订单规则、状态转换和值对象
    application/
      create-order         # 创建订单用例：编排业务与副作用
      order-store          # 用例需要的最小持久化契约
    adapters/
      order-http           # 请求校验、协议转换、响应映射
      sql-order-store      # 持久化契约的具体实现
  bootstrap/               # 构造依赖、注册路由、启动应用
```

测试按仓库惯例同目录或镜像放置。迁移文件、静态资源、框架路由保留工具要求的位置。

静态依赖方向为：

```text
application → domain
adapters → application 的契约、domain
bootstrap → 各模块的装配入口与具体适配器
```

运行时由用例调用注入的存储实现，但用例不导入 SQL 实现。公开业务入口和装配入口可以分开，以免业务调用方被迫加载具体基础设施。

## 拆分与共享准则

- 规则放在拥有该业务概念的模块，其他模块使用其公开能力，避免多处分别维护同一规则。
- 存储模型、HTTP 请求对象和业务对象仅在表示方式或生命周期确有不同时分离，不为简单字段复制制造多套模型。
- 对普通公共工具目录，仅提取职责明确、语义稳定的共享能力，不因两处代码相似就迁入。框架定义的 `shared` 按框架用途执行，可以包含允许跨端共享的业务类型；它不承担后端内部规则的所有权。
- 不按任意行数强制拆文件，优先检查职责是否混杂、导航是否困难、修改是否牵连无关功能。
- 跨模块事务和一致性由业务要求决定，先考虑现有事务与直接调用，确有异步解耦需求时才引入事件机制。

## 渐进调整既有项目

找到本次涉及的业务入口、规则和副作用，在现有模块内提取最小边界。保持公开行为，更新调用方并验证。只有当前目录明确阻碍本次需求时才移动文件，并处理导出、路径别名、构建配置和测试引用。
