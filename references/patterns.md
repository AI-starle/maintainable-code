# 按问题选择设计模式

先识别实际问题，再选择模式。评估已有抽象时也使用同一标准：它是否隔离了真实变化或外部边界，调用方是否因此更易理解。下表是判断依据，不是必须使用的清单。

| 模式或手段 | 当前问题 | 最小实现 | 不宜引入的情况 |
| --- | --- | --- | --- |
| Strategy（策略） | 同一步骤有多种可替换算法，且独立变化 | 函数参数、策略映射或小接口 | 只有一个实现，简单分支已清晰 |
| Adapter（适配器） | 第三方 SDK、协议或历史接口与内部契约不一致 | 在边界转换输入、输出和错误 | 接口已匹配，增加一层仅转发调用 |
| Factory（工厂） | 创建对象涉及配置分支或多步装配，并在多处使用 | 工厂函数，必要时返回契约类型 | 直接构造足够清晰，或只在单一入口装配 |
| Repository / Store | 用例需要隔离查询与持久化细节 | 按业务需要定义少量存取方法 | 当前无隔离收益，只是为每张表生成通用 CRUD 基类或包裹 ORM 同名方法 |
| State（状态） | 生命周期有明确合法转换，各状态行为显著不同 | 先用显式状态与转换表，复杂时拆对象 | 状态少且规则简单，枚举与条件已足够 |
| Decorator（装饰器） | 重试、缓存、计时等行为需要围绕同一契约组合 | 包装函数或对象，保持契约 | 顺序和错误语义无法明确，或框架已有机制 |
| Facade（门面） | 调用方需跨多个内部组件完成连贯任务 | 暴露面向用例的少量方法 | 形成掌握所有业务的巨型 Service |
| Observer / 领域事件 | 多个独立消费者响应同一事实，确有解耦需求 | 明确事件类型、发布边界和消费者 | 关键同步步骤需直接反馈，事件隐藏控制流 |

## 具体约束

- 策略和工厂优先使用语言原生函数与组合，不强行套用类层次。
- Repository 契约由用例需要决定，避免向核心暴露 ORM 查询构造器、连接对象或持久化实体。
- 自动重试考虑幂等性、次数、超时和取消；缓存明确键、有效期与失效规则。不将这些行为作为默认“增强”悄悄加入。
- 事件明确事务提交前后的发布时机。异步交付按需求考虑重复消费、失败恢复与顺序，不将同步调用改为事件就声称已解耦。
- 不默认使用 Singleton 或 Service Locator 传递依赖；优先在组合入口创建实例并显式传入，保持生命周期和测试替换清晰。
- 项目已有适用的模式时优先延续，避免同一变化点出现两套竞争抽象；也不只因既有代码使用某种模式，就把它扩展到无关简单逻辑。
- 不堆叠多种模式解释一个简单问题。每个抽象应对应当前存在的调用方、变化点或业务边界。

## 取舍表达示例

“目前有两种计价规则，且各自独立变化，因此将计价步骤作为策略函数传入结算用例；暂不引入策略类和注册中心。”

“当前只有一个存储实现，但业务规则需脱离数据库独立验证，因此定义由用例消费的最小 Store 契约，在启动入口注入 SQL 适配器。”

“当前只是单一步骤的数据转换，直接使用纯函数，不增加工厂、接口和服务层。”
